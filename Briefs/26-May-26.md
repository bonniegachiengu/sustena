### 🤖 AN1 — DEEP: Claude Managed Agents (Dreaming, Outcomes, Multiagent Orchestration)

**What actually shipped at Code with Claude (May 6, 2026)**

#### Dreaming

Dreaming is a scheduled background process — not a feature you call manually.
It runs on your agent's memory stores, reviews past sessions, extracts patterns,
and writes curated learnings back into the agent's memory.

What it surfaces:
- Recurring mistakes the agent makes across users
- Workflows that consistently produce good outcomes
- Team preferences that appear across many sessions

**Status:** Research preview — requires a separate access request.

**Sustena relevance:**
This is almost exactly what Sustena's Observe → Model loop needs for
persistent operative improvement. Before building your own version of this
from scratch, apply for the Dreaming research preview and evaluate whether
the hosted Anthropic version can serve as the self-improvement engine for
Sustena operatives. If it can, you save 3–4 sprints of custom work.

---

#### Outcomes

You write a rubric — a plain-language description of what "success" looks like.
A separate grader model reads the output in its own context window (isolated
from the agent's reasoning chain) and scores it against your rubric.

Key design choice: the grader is isolated so it can't be influenced by the
agent's own reasoning. This prevents the agent from gaming its own evaluation.

Real-world result: Wisedocs is reviewing medical documents 50% faster.
Harvey reported a 6x jump in task completion rates using Outcomes.

**Status:** Public beta — available now via the Claude Platform API
with the `managed-agents-2026-04-01` beta header.

**Sustena relevance:**
This is Sustena's Simulate → Optimise loop in hosted form. The Outcomes
rubric format maps directly to how Sustena's Constraint primitives define
success criteria. You could use Outcomes as the evaluation engine for
Biashara Sustain's financial goal-checking without writing a custom evaluator.

---

#### Multiagent Orchestration

A lead agent breaks a job into pieces and assigns each to a specialist subagent
with its own model, prompt, and tools. Specialists run in parallel on a shared
filesystem and contribute back to the lead agent's context.

Limits: up to 20 unique specialist subagents, up to 25 concurrent threads.

Example: lead agent runs an investigation while subagents fan out through
deploy history, error logs, metrics, and support tickets simultaneously.

**Status:** Public beta.

**Sustena relevance:**
This is Sustena's Council DAO pattern in hosted form. The 20-subagent / 25-thread
limit is adequate for Phase 1 Sustena workloads. The shared filesystem model maps
to how Sustena's State primitive needs to work across operative sessions. Consider
whether Multiagent Orchestration can serve as Sustena's execution engine in Phase 1
before you build the full custom Council DAO — it would let you validate the pattern
with real users faster.

### 🤖 AN2 — DEEP: Claude Platform on AWS

**What it is:**
Claude Platform on AWS is a new deployment model where Anthropic operates
the service (not AWS) but hosts it within AWS infrastructure. Key distinction:
data is processed outside the AWS boundary — Anthropic owns the stack.

**Why this matters for Sustena:**

From day one, it gives AWS-deploying developers access to all native Claude API
features — Managed Agents, Files API, MCP Connector, Opus limits — without
waiting for AWS Bedrock to catch up on feature parity.

Previously, AWS Bedrock lagged the Claude API by weeks or months on new features.
This eliminates that gap for any team running on AWS infrastructure.

**Practical implication for Sustena:**
If you plan to host Sustena's backend on AWS (which is common for East Africa
deployments due to the Cape Town region), you can now use the full Claude
feature stack without compromise. This changes the infrastructure decision:
AWS is now a first-class deployment target, not a compromise.

### 🛠️ T1 — DEEP: MCP Gateways — Relevance and Application to Sustena

**EXP: What is an MCP Gateway?**

MCP (Model Context Protocol) is the standard for connecting AI agents to tools —
databases, APIs, file systems, external services. An MCP server wraps a tool and
exposes it to an agent. An MCP gateway sits in front of multiple MCP servers and
acts as the control layer — authentication, rate limiting, access policy, logging.

Think of it like an API gateway (Kong, AWS API Gateway) but specifically for
AI agent tool access.

**Why this matters specifically for Sustena:**

Sustena's architecture has Operatives (AI agents) that need to use tools
(M-Pesa, WhatsApp, Firestore, market data feeds, IoT sensors). Right now,
in Phase 1, each Operative connects directly to its MCP server.

The problem that emerges at scale:
- Different tenants (different Sustain deployments) should only access their own tools
- You need to rate-limit tool calls per tenant so one customer can't exhaust the API budget
- You need a central audit log of every tool call for debugging and compliance
- You need to rotate credentials without redeploying individual operatives

An MCP gateway solves all of this in one layer.

**Concrete application — what to build:**

```
[Sustena Operative] → [Sustena MCP Gateway] → [M-Pesa MCP Server]
                                             → [WhatsApp MCP Server]
                                             → [Firestore MCP Server]
                                             → [Mycelium Marketplace MCP Servers]
```

The gateway enforces:
- Tenant credential scoping (Biashara tenant can't call Mkulima's M-Pesa creds)
- Rate limits per tenant per tool
- Audit log for every tool call (needed for CBK compliance in Phase 3)
- Tool discovery (Mycelium's OperativeRegistry becomes a gateway registry)

**What to build in Phase 1 vs. what to defer:**

Phase 1 (SQLite/local): A lightweight gateway is a thin auth + logging wrapper.
Don't over-engineer it. Build it as a FastAPI middleware layer.

Phase 2 (multi-tenant): The gateway becomes critical. This is when
you need per-tenant credential scoping and rate limiting properly.

Phase 3 (Mycelium marketplace): The gateway IS the Mycelium OperativeRegistry —
every third-party tool plugs in here, the gateway handles discovery + licensing.

**Open-source options to evaluate now:**
- MCP Gateway (open source, 2026) — basic auth + routing
- Composio Tool Router — dynamic MCP tool discovery
- Build lightweight in-house: 2–3 days in FastAPI, keeps you in control

### 🇰🇪 K1 — DEEP: Finance Bill 2026 M-Pesa VAT — Implications + Alternatives

**ANA: What it actually means**

The Finance Bill 2026 (tabled May 5, effective July 1 if passed) proposes
16% VAT on fees charged by all 42 licensed payment service providers.

Important nuance: the VAT is on the transaction fee, not the transaction itself.
Example: a KES 108 M-Pesa fee would attract KES 17 additional VAT on top.
M-Pesa fees already carry 20% excise duty — this stacks on top of that.

Volume in FY ending March 2026: KES 41.7 trillion moved, 46.4 billion transactions.

**Exemptions confirmed:**
Fuliza and M-Shwari remain VAT-exempt (they route through bank partnerships).

**Risk assessment:**

| Risk | Likelihood | Severity |
|------|-----------|---------|
| Bill passes unamended July 1 | Medium | High |
| Consumer backlash forces amendment | Medium | Medium |
| Operators absorb cost (margin squeeze) | Low | Low for users, high for Safaricom |
| Cash-back shift reduces digital transaction volume | High if passed | High for Sustena |

**Kenya Bankers Association warning:**
"You tax digital payment platforms, you drive consumers to the mattress and
the informal economy." This would reduce the formal transaction data Sustena's
financial operatives depend on.

**Alternatives and mitigation for Sustena:**

1. **Design for bank-rail fallback now.**
   If M-Pesa gets expensive, volume shifts to bank transfers (Pesalink, RTGS).
   Sustena's Daraja integration should be paired with Pesalink support from Phase 2.

2. **Use Fuliza/M-Shwari-adjacent flows where possible.**
   These are VAT-exempt. For credit-linked payments in Biashara Sustain,
   routing through bank-M-Pesa partnerships avoids the VAT layer.

3. **Watch the parliamentary timeline.**
   The bill has until June 30 to be passed, rejected, or amended. The KBA
   and tech industry are lobbying hard. There's a realistic chance the
   mobile money clause gets amended or dropped — as happened to several
   clauses in the Finance Bills of 2023 and 2024 after public pushback.

4. **For Vyyb specifically:**
   Vyyb's payment volume is relatively small at launch. Even if the VAT passes,
   the actual cost impact on Vyyb in the first 6 months is minor (hundreds of KES,
   not thousands). The structural risk is the consumer behaviour shift — if Kenyans
   move back to cash, Vyyb's WhatsApp ordering and delivery payment model suffers.
   Mitigation: ensure cash-on-delivery remains an option for all Outlet and
   delivery orders, even as you push digital.

### 🌐 W1 — SUM: Kenya VASP Regulations 2026 (Plain Language)

**What's happening:**
Kenya is finally writing official rules for cryptocurrency businesses.
The consultation (public comment period) closed in April 2026.
Final rules are expected to be published soon.

**The basic structure — two regulators:**
- **CBK** handles anything that looks like money: stablecoins (crypto pegged to KES/USD),
  payment apps using crypto, crypto-linked savings products.
- **CMA** handles everything else: crypto exchanges (buy/sell platforms), brokers,
  token issuers, tokenized assets (real estate, stocks, etc.).

**What it costs to operate:**
To issue a stablecoin in Kenya, you need KES 500 million (~$3.86M) in minimum capital.
Foreign companies must get a local compliance certificate before operating.

**The controversy:**
Local startups say this pricing structure only works for large international players —
Binance, Coinbase, etc. — and locks out Kenyan founders. The Virtual Asset
Association of Kenya (VAAK) has formally objected.

**What this means for Sustena's Phase 3 (Pawa ERC-20):**
Pawa is a utility token, not a stablecoin, so the KES 500M rule likely doesn't apply
directly. But you'd still need CMA licensing to operate an exchange or tokenized
asset platform. The CMA Sandbox is the right starting point — it gives you 12–24 months
to operate under lighter rules while the full licence is processed.
Start the sandbox application research in Phase 2, not Phase 3.
